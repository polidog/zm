Zoom MCP 計画
Project plan · 2026-10-27

Zoom ペダルを MCP で鳴らす

Goal

G2 FOUR / MultiStomp の音作りを、Claude から MCP ツール経由で操作できるようにする。実行環境は Omarchy（Arch Linux + Hyprland）。

TARGET: ZOOM G2 FOUR（第一候補） TRANSPORT: USB class-compliant MIDI / SysEx CORE: Python + Construct
01 · Architecture

信号の流れ

作るものは 4 層。難しさのほとんどは真ん中の 2 層（コーデックとエフェクトカタログ）に集まる。

L1

トランスポート

ALSA rawmidi または mido で SysEx を送受信する。Linux はクラスコンプライアントなので、ドライバ問題はまず起きない。一番楽な層。

L2

コーデック核心

SysEx の 7bit パック解除と CRC、パッチ構造（スロット数・エフェクト ID・パラメータ値・パッチ名）の双方向変換。ラウンドトリップでバイト一致させる。

L3

エフェクトカタログ核心

「ID 0x0123 = MS Drive、param[0] = Gain 0–100」という辞書。ここが人間の言葉で揃っていないと、MCP で「音作り」は成立しない。

L4

MCP サーバー

プリミティブなツール群とカタログリソースを公開する。曖昧な指示（「80 年代っぽいクリーンに」）の解釈は Claude 側に任せ、サーバーは素直に保つ。

02 · Existing work

流用できる解析資産

Zoom は SysEx 仕様を公開していないが、コミュニティの解析は厚い。各資産がどの層を埋めるかで整理する。

thammer/zoom-explorer

fills: L1 · L2 (protocol)

MS＋シリーズ向けに一番整理された MIDI 仕様表。Identity Request、パッチダンプ、現在パッチ送信、スロット選択、テンポ、スロット移動まで。ブラウザで動く解析ツール付き。

mungewell/zoom-zt2

fills: L2 · L3 (patch / ZD2)

Four シリーズ解析の本家。Python Construct でパッチと ZD2 を定義。B2 FOUR が G1/B1 FOUR とほぼ同プロトコルと判明しており、同世代の G2 FOUR も乗る見込み。

zoom_fx_AllZDL7/master.txt + ZD2

fills: L3 (catalog source)

エフェクト名・パラメータ名の元ネタ。ペダルから取り出した ZD2 自体にも入っているので、カタログを全部手書きする必要はない。

PedalPi/PluginsManager-Zoom

fills: L4 (API design ref)

connect → load_data → パラメータ変更 → 機器側の変更も受信、という API 設計の先行例。対象は G3 だが、MCP ツールの粒度を決める参考になる。

g200kg/zoom-ms-utility

fills: 旧 MS シリーズ (別系統)

旧 MS-50G/60B/70CDR 用の Web エディタと midimessage.md。旧世代は別プロトコルなので、対応するならこちらを参照する。

shooking/ZoomPedalFun

fills: 解析ノウハウ

Linux + Python + Wireshark でのキャプチャ手順と周辺プロジェクトのリンク集。G2 FOUR で空白が見つかったときの作業手引き。

03 · Protocol cheat sheet

Phase 0 で投げるバイト列

MS＋/Four 系で確認されているメッセージ。デバイス ID 6E は MS-50G+ と G1 FOUR で共通。G2 FOUR で同じ応答が返るかが最初の分岐点になる。

sysexwhat
F0 7E 7F 06 01 F7Identity Request → 機種 ID と OS バージョン
F0 52 00 6E 33 F7現在のバンク / プログラム番号を取得
F0 52 00 6E 46 00 00 bL bM pL pM F7指定バンク / プログラムのパッチをダウンロード
F0 52 00 6E 64 13 F7現在パッチのダンプを要求（応答は 64 12）
F0 52 00 6E 28 F7現在パッチをペダルへ送る（保存しない）
F0 52 00 6E 64 20 00 64 01 slot 00 00 00 00 F7エフェクトスロットを選択
F0 52 00 6E 64 20 00 64 02 bL bM 00 00 00 F7テンポ (BPM) の取得 / 設定
04 · Phases

進め方

P0疎通確認 · 1 日

G2 FOUR が既知のプロトコルに乗っているか確かめる

  • amidi -l でポートを確認し、Identity Request を投げて機種 ID と OS バージョンが返るか見る
  • zoom-explorer を Chromium で開き、パッチダンプが取れるか試す
  • この時点で全パッチのフルバックアップを取り、以降の実験の保険にする
乗っていなければ Wireshark でのキャプチャ作業が先
P1読み出し専用コア

dump_patch(n) → JSON

  • zoom-zt2 の Construct 定義をベースに、パッチを JSON へ変換する
  • 実機パッチをダンプ → JSON → 再エンコードでバイト一致するか、ラウンドトリップテストを自動化
  • 読むだけなのでペダルを壊すリスクがほぼない
read-only · 安全
P2エフェクトカタログ

ID → 名前 / パラメータ / レンジ の辞書を作る

  • ペダルから ZD2 一覧を取得し、エフェクト名・パラメータ名・レンジを抽出して YAML / JSON 化
  • 各パラメータに人間向けの説明文を足す（ここは Claude に手伝わせる）
  • このカタログが MCP のリソースになる
read-only · 安全
P3書き込み

送るだけ → 保存 の順で段階的に

  • まず「現在パッチをペダルに送る」から。保存しないので電源を落とせば戻る、という安全弁付き
  • 次にパッチ保存。ラウンドトリップが通っているバイト列しか書かない
  • エフェクトファイルの追加・削除（フラッシュ操作）は当面スコープ外
flash write · 慎重に
P4MCP サーバー

プリミティブなツール群として公開

  • Python の mcp パッケージで、下表のツールとリソースを実装
  • サーバーは素直な操作に留め、曖昧な指示の解釈は Claude 側に任せる
  • Claude Code / Claude Desktop に登録して、会話から音作りする
P5任意

Omarchy 向け TUI

  • ratatui など、同じコアライブラリの上に TUI を乗せる
  • MCP と TUI がコアを共有する構成にし、Hyprland のタイル表示に馴染ませる
プロトコルが固まってから

06 · Open questions

先に決めたいこと

手元の実機は何か

G2 FOUR だけか、MS-50G+ や旧 MS-50G もあるか。旧 MS は別プロトコルなので、対応範囲で工数が変わる。

最初のターゲット機種

G2 FOUR 一本で始めるのを推奨。解析の空白が一番大きく、埋めれば価値も大きい。

言語

解析資産が Python (Construct) に集中しているのでコアは Python、MCP も mcp パッケージで揃えるのが最短。Rust / Go はプロトコルが固まってから。

安全策

P0 で全パッチをバックアップ。書き込みは「送るだけ」から始め、フラッシュ操作は当面触らない。
